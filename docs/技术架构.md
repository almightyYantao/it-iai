# 爱 AI · 技术架构

> 内部一键部署平台。开发者一行命令，3 分钟内拿到带 SSO + HTTPS 的可访问 URL。

---

## 一、为什么需要这个东西

公司内部研发同学想把一个项目（前端 demo / AI agent / 内部工具）跑起来给团队用，传统流程：

1. 申请 ECS
2. 写 Dockerfile
3. 配 K8s YAML（Deployment / Service / Ingress / TLS）
4. 配 CI/CD
5. 申请域名 + DNS
6. 接 Keycloak SSO

对一个想快速验证想法的人来说，门槛太高。从想法到能给别人看一眼，经常按周计。

**爱 AI** 把这条链路压缩成一条命令：

```
cd <project>
# 在 Claude Code 里说 "部署一下"
```

约 1-3 分钟后，拿到 `https://<your-name>.example.com/`，自带：

- HTTPS（通配证书 + Traefik 自动 80→443 跳转）
- Longbridge Account 单点登录（oauth2-proxy + Keycloak）
- 可选的 IP 白名单（CIDR 预设或自定义）
- 实时构建/运行日志（SSE 流）
- 协作者管理、自定义域名、审计日志

**全程不写 Dockerfile，不碰 K8s。**

## 三、一次部署的完整链路

最常见的「在 Claude Code 里说部署一下」是这么走的：

### 3.1 Skill 端（开发者本机）

Skill 代码独立维护在 [it-iai-skill](https://github.com/almightyYantao/it-iai-skill)；主仓的 `skill/` 是指向它的 submodule。`scripts/push.sh` 完成：

1. **扫描**：递归识别项目类型（Node.js / Python / Go / Rust 等），生成 manifest（name / port / build / start / 需要哪些 sidecar）。优先级：`.vibedeploy.toml` 显式声明 → 框架特征 → 兜底默认值
2. **打包**：git 仓库走 `git ls-files`（自动尊重 .gitignore）；非 git 仓库手工 exclude + `.deployignore`；zstd 压缩成 `source.tar.zst`
3. **创建项目**（首次推送）：调 `POST /v1/projects`，拿到 slug；后续推送复用 `.vibedeploy.json` 里记的 slug
4. **创建部署**：调 `POST /v1/projects/{slug}/deployments`，服务端生成 deployment ID、签发**预签名 MinIO PUT URL**、**SSE 流 URL**
5. **上传**：`curl -X PUT` 把 tarball 传到预签名地址（**不经过 control-plane**，绕开代理瓶颈）。地址的 host 是 `CP_S3_PUBLIC_ENDPOINT`——现在指向 admin 域名，由 admin UI 的 nginx 按 `/<bucket>/` 前缀反代到 MinIO，因为 MinIO 自己的 9000 端口对开发机不开放。SigV4 把 Host 和 URI 路径都签进签名，所以反代必须原样透传两者，且预签名必须用 path-style（见 `internal/storage/minio.go` 的 `BucketLookupPath`）；任一条不满足会得到 `SignatureDoesNotMatch`，而不是路由错误
6. **通知**：调 `POST /v1/projects/{slug}/deployments/{id}/uploaded`
7. **流式跟踪**：订阅 SSE，把 `[phase] message` 逐行打到终端，直到 `event: end`

### 3.2 Control-plane（调度大脑）

Go + chi + pgxpool，HTTP API 一个进程，外加一个 reconciler 后台 goroutine。

`reconciler.go` 跑**两个 loop**：

| Loop | 周期 | 作用 |
|---|---|---|
| `tick`            | 2s  | 推进 `pushing` / `deploying` 状态：写 K8s manifest、监 pod、ready → running |
| `runHealthLoop`   | 30s | 重新探测所有 `running` 项目的 pod，DB 状态与真实不一致时纠正 |

第二个 loop 是为了对抗：用户手动 `kubectl scale --replicas=0`、节点驱逐、pod OOM 后没拉起来等场景——control-plane 必须能持续校准，不能让 DB 永远显示 running。

两个 loop 的取数都**必须过滤 `deleted_at IS NULL`**，和其他所有项目读路径保持一致：

- `tick` 的 deployments 查询 join `projects` 过滤软删项目。否则一条卡在 `pushing` / `deploying` 的 deployment 会让已软删项目被重新 apply——namespace 被重建，ready 之后又把 `status='running'` 写回墓碑行。
- `slugFor` 同样过滤；查不到就让该 deployment 失败，而不是往一个已不存在的项目里部署。

漏掉过滤的后果不是「多跑一个 pod」，而是产生**平台管不着的活负载**：它不出现在任何列表查询里，`reconcileProjectHealth` 和启动时的 ingress sweep 也都跳过它（两者都过滤 `deleted_at IS NULL`），于是健康状态不再纠偏、TLS / CIDR 策略变更不再下发，owner 调管理接口只会拿到 404。排查手法见[运维手册 §7](./运维手册.md)的集群 / DB 对账。

### 3.3 Build-service

- 从预签名 URL 拉 tarball
- 跑 [nixpacks](https://nixpacks.com)：自动识别语言、生成构建 plan、产出标准化镜像（**用户无需写 Dockerfile**）
- `docker push` 到本地 registry（监听 `127.0.0.1:5001`，docker daemon 默认信任 loopback，零配置）
- 推 deployment 到 `pushing` 状态，reconciler 接手

### 3.4 K8s driver

`internal/k8sdriver/deployer.go`，client-go 的薄壳：

- `EnsureNamespace`：每个项目独立 namespace `proj-<slug>`，**天然隔离**
- `Apply`：写 Deployment / Service / Ingress（默认子域 `<slug>.example.com`）+ 可选 Secret（用户 env）
- `SyncIngressHostnames`：自定义域 + IP 白名单 + ForwardAuth 中间件链
- `PodSummary` / `PodPlacement`：给 UI 提供 pod 状态 & 节点位置

镜像 tag 在 apply 前会被 `rewriteImageHost` 改写：build-service push 用 `127.0.0.1:5001`，K3s 节点拉用 `<PLATFORM_IP>:5001`，避免 worker 解析不到 loopback。

### 3.5 Traefik 入口

每个节点都跑 Traefik DaemonSet，`hostNetwork: true` 直接绑 :80 / :443。

`dnsPolicy: ClusterFirstWithHostNet` 是关键——`hostNetwork` 默认走宿主 `/etc/resolv.conf`（云上指向云厂商 DNS，解析不到 `*.svc.cluster.local`），加这个才能让 Traefik 通过 CoreDNS 访问 oauth2-proxy 等集群内服务。

**Middleware 链**按入站方向：

1. **IP allow-list**（IPAllowList CRD）—— 不在白名单内的源 IP 在这里就被拒了，**不会**继续打到 oauth2-proxy
2. **errors-redirect** —— 把下游 401 转换成 302，跳到 `/oauth2/start`
3. **forward-auth** —— 调 oauth2-proxy `/oauth2/auth`，200 放行 / 401 触发上面的 errors

所有项目都挂这套链。（`public` 可见性——跳过 #2、#3 完全免 SSO——已于 2026-07 停用。）

### 3.6 用户 pod 的出站限制

上面那套链管的是**进来的**流量。出去的流量由每个项目 namespace 里的 `iai-egress` NetworkPolicy 管，由 `Apply` 每次部署自动写入（`ensureEgressPolicy`）。

要解决的问题：平台把 registry(5001)、控制面 Postgres(5432)、控制面 API(8080) 都发布在宿主的 `0.0.0.0` 上，任何用户负载都能直连。其中 registry 无认证——pod 可以枚举全部镜像，甚至往任意 repo 推 tag 覆盖别人的项目；控制面 DB 里有 token hash、`project_env` 密文和审计。

**为什么不能用宿主防火墙**：pod 访问节点 IP 时，源地址在到达宿主前已被 masquerade 成该节点的 IP，registry 根本区分不了「pod」和「containerd」。按源 IP 拦要么放过 pod，要么连节点拉镜像一起拦死。所以必须在 pod 出口拦。

NetworkPolicy 只有 allow-list，所以「封几个端口」的写法是：先放通「除平台地址以外的全部网段」，再把平台地址按 pod 真正需要的端口加回来——端口取自 `CP_USER_PG_PUBLIC_HOST` / `CP_USER_REDIS_PUBLIC_HOST` / `CP_USER_S3_PUBLIC_HOST` / `CP_S3_PUBLIC_ENDPOINT` 加 80/443。没被授予的端口（5001 / 5432 / 8080 / 5173）自然不可达。

两个已知限制：

- **规则下发晚于 pod 启动。** kube-router 在 pod 创建后才编程 iptables，实测短命 pod 能在规则生效前完成一次外连。判断策略是否生效时要用长驻 pod 测，否则会得到假阴性。
- **配成主机名的 endpoint 会被跳过。** `ipBlock` 无法表达 DNS 名，这类 endpoint 落到兜底规则里保持放通——宁可放过也不误伤没解析出来的服务。

巡检和临时下发见[运维手册 §7](./运维手册.md)。

## 四、认证体系

两条入口：

### 4.1 Deploy Token（Skill / CI 用）

- 格式：`vbd_live_<32-bytes-rand>`，存 `~/.vibedeploy/credentials.json`（0600）
- 服务端只存 `bcrypt(token)` + 前缀，**原文不落地**
- 支持 scopes（admin / project-scoped）和过期时间

### 4.2 OIDC code flow（Web UI 用）

- 走 Keycloak（公司 SSO 叫 "Longbridge Account"）
- **HMAC 签名 state**——state 参数自包含 + 签名校验，不依赖 cookie，**绕开跨端口 / 跨子域 cookie scope 问题**
- 拿到 access_token 后用 JWKS 验签 + 校验 audience + issuer
- 用 token claims 里的 email upsert 到 users 表

### 4.3 用户应用的访问控制

两层：

| 层 | 怎么做 | 拦在哪里 |
|---|---|---|
| **L4**（网络） | Traefik IPAllowList Middleware | CIDR 不匹配的源直接 403 |
| **L7**（身份） | Traefik ForwardAuth → oauth2-proxy → Keycloak | 未登录 302 跳 SSO |

**CIDR 白名单**数据模型上支持两种模式：

- **预设模式**：管理员在 `设置 → 访问预设` 维护命名预设（系统自带 `public` / `internal`，可自建）。项目 `access_preset` 指向某个预设，**改一处所有引用项目自动重新挂载**
- **自定义模式**：`access_preset` 为 NULL，项目用自己的 `allow_cidrs`，用于特例

#### per-project 自助已停用

「访问控制」面板已从项目页移除，`PATCH /v1/projects/:slug/access` 和 `PATCH /v1/projects/:slug/visibility` 一律返回 `403 access_policy_frozen`，开关是 `accessPolicySelfService`（`internal/api/project_actions.go`）。

**为什么两边都要动**：只隐藏 UI 等于把同一个能力挪到裸 API 调用后面——任何拿着 owner token 的人照样能改。所以 handler 也加了守卫，两处由同一个常量控制，要恢复自助只改这一行。

现在的维护路径：新项目默认落到 `internal` 预设（migration 0010），需要调整范围时管理员改预设内容（`PUT /v1/admin/cidr-presets/{name}`，会 resync 所有引用它的项目）。这条路径没有被冻结。

两个后果要知道：

- **`visibility` 也一起冻结了**，因为它渲染在同一个被移除的面板里（「登录要求」）。项目 owner 不能再自己切 `org` ↔ `restricted`。
- **仍指向 `public` 预设的存量项目改不动了。** `public` 是 `is_system` 预设、API 层删不掉（删掉会因 FK `ON DELETE SET NULL` 把项目静默转成「自定义空列表」，同样无限制但连模式都看不出来）。它的 CIDR 列表是空的，语义是**没有网络层限制**。要迁移这类项目，只能改 DB 再触发 ingress resync，见[运维手册 §7](./运维手册.md)。

## 五、用户应用的数据 · 自动开通 + 真隔离

manifest 声明 `needs.{postgres,redis,s3,sqlite} = true`，平台 reconcile 时自动开资源、把凭据加密注入 pod。四个能力共享底座，但每项目拿到**真隔离**的切片：

| 服务 | 共享底座 | 每项目派生 | 隔离机制 | 注入到 pod 的 env |
|---|---|---|---|---|
| Postgres | `user-postgres` 容器（独立于控制面 PG） | DB `proj_<slug>` + role + 随机 password | SQL 层 `GRANT` 只到自家 DB | `DATABASE_URL` |
| Redis | shared `redis` 容器（Redis 6 ACL） | ACL user `proj-<slug>` + 限 `~proj-<slug>:*` + `-@dangerous` | ACL 层；前缀外 key 直接 NOPERM | `REDIS_URL` + `REDIS_KEY_PREFIX` |
| MinIO | shared `minio` 容器（复用平台底座） | bucket `proj-<slug>` + IAM user + bucket-only policy | IAM policy 锁定 | `S3_ENDPOINT` / `S3_REGION` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` / `S3_BUCKET` / `S3_USE_SSL` |
| SQLite | pod 内 `emptyDir /data` + Litestream sidecar（复用项目自家 MinIO bucket 作 replica 目标） | init container 启动时 `litestream restore -if-replica-exists`；sidecar 持续 `litestream replicate` 增量同步 | 复用 MinIO 的 IAM 隔离（数据物理上就在项目自家 bucket 里） | `SQLITE_PATH=/data/app.db` + 复用 S3_* |

> SQLite 声明 `needs.sqlite=true` 时 reconciler 会**自动隐式** `needs_s3=true`：Litestream 没 S3 没法工作。用户不用关心这个依赖关系。

### 5.1 Provision 链路

```
deploy push → reconciler 看 m.Needs
  │
  ├── postgres: pgxpool admin URL → CREATE ROLE + CREATE DATABASE + GRANT
  │              ↓
  │              DATABASE_URL → store.SetProjectEnv(system=true) 加密落 DB
  │
  ├── redis: go-redis admin URL → ACL SETUSER ~prefix:* -@dangerous
  │              ↓
  │              REDIS_URL + REDIS_KEY_PREFIX → SetProjectEnv
  │
  ├── s3 (||= sqlite): madmin + minio-go → bucket + canned policy + AddUser + AttachPolicy
  │              ↓
  │              6 个 S3_* env vars → SetProjectEnv
  │
  └── sqlite: deployer 在 PodSpec 加：
                 - emptyDir volume `sqlite-data` 挂到 /data
                 - init container `litestream/litestream:0.3.13` 跑 restore
                 - sidecar container 跑 replicate（共享 app-env Secret 拿 S3 creds）
                 - app container 注入 `SQLITE_PATH=/data/app.db`
```

写完之后 reconciler 把 `project_env` 整体（manifest.env + 自动派生项）merge 进 K8s Secret，pod rolling-restart 时 attach。所有 SetProjectEnv 都用 `system=true` 标记，Web 后台不允许人工编辑/删除这些行——避免 admin 误覆盖把应用搞挂。

### 5.2 幂等 & deprovision

每个 provisioner 都幂等：

- **PG** `Provision`：role / database 存在则保留，只 rotate password
- **Redis** `Provision`：`ACL SETUSER` 本身是 upsert，重跑等于改密码
- **S3** `Provision`：bucket 存在则保留，user `AddUser` 是 upsert（rotate secret），policy `AddCannedPolicy` upsert

项目删除（`handleDeleteProject`）时反向调用：

- **PG**：先 `pg_terminate_backend` 砍 live 连接，然后 `DROP DATABASE` + `DROP ROLE`
- **Redis**：`ACL DELUSER` + `ACL SAVE` 持久化
- **S3**：detach policy + remove user + remove canned policy；**bucket 保留**（误删损失太大，admin 确认后再 `mc rb --force`）

每一步失败都进 audit log，不阻塞软删——orphan 资源比"项目卡在 deleting 状态"更可接受。

### 5.3 为什么不每项目一个 PG / Redis pod

考虑过、否掉了。

- Per-project StatefulSet 每个项目就是一个 PG pod + PVC（~200MB RAM 起，PVC 管理复杂、节点资源占用快速膨胀）
- 50 个项目就是 50 个 PG 实例，对内部工具平台严重 over-engineering
- 共享 + ACL 已经能拿到 SQL/ACL/IAM 层的真隔离，性价比远高
- 真的有项目需要专属实例（合规要求 / 大容量），用户自带 RDS + 在 Web 后台环境变量面板手填 DATABASE_URL 即可，绕开自动 provision

## 六、运行时配置热加载

平台关键配置（Keycloak issuer / client / 网关 cookie domain 等）以前要改 `.env` + 重启容器。现在：

```
启动            管理员保存 Settings 页
  │                   │
  ▼                   ▼
读 env 默认值     PATCH /v1/admin/settings
  │                   │
  ▼                   ▼
overlay DB 行   → 写 system_config 表
  │                   │
  ▼                   ▼
内存 KCSettings ← Runtime.Reload(ctx)
  │                   │
  ▼                   ▼
OIDC handlers     atomic.Pointer 替换 JWT 验签器
读 runtime.KC()        ↓
                  零停机生效
```

关键实现：

- `system_config (key, value, updated_at, updated_by)` 表存所有可变配置
- `internal/config/runtime.go` 维护 RWMutex 守的内存视图
- JWT 验签器通过 `atomic.Pointer[JWTVerifier]` 热替换
- 敏感字段（client_secret / cookie_secret）在 GET 接口返回 `********`，PATCH 时收到 `********` 视为「保持原值」，避免误覆盖

## 七、部署拓扑

当前架构：

| 节点 | 角色 | 跑什么 |
|---|---|---|
| 平台节点 ×1 | K3s server | docker-compose（control-plane / build-service / postgres / minio / registry / redis / web）+ K3s server 二进制 |
| Worker ×N | K3s agent | 仅 K3s agent，跑用户应用 pod |

**单节点也能跑**——server 上没有 NoSchedule taint，用户 pod 也能调度到平台节点；只是不建议长期这样。

每个组件之间已经是**网络解耦**（postgres 走 URL，minio 走 S3 endpoint，registry 走 host:port），所以扩容不需要重写代码，主要是运维动作：

| 阶段 | 做什么 | 工作量 |
|---|---|---|
| **阶段 0**（现在） | 单平台节点 all-in-one | — |
| **阶段 1** | PG / MinIO / Registry 拆到外部（RDS / OSS / ACR） | ~0.5 天 |
| **阶段 2** | build-service 多实例 + 并发构建 | 1-2 天（换 Kaniko 是 3-5 天） |
| **阶段 3** | control-plane HA（多副本 + SLB）+ K3s server 三节点 etcd | 1 天 |

**阶段 1 是收益最大的一步**：平台节点变无状态，磁盘炸了重装一台、`git pull` + `docker compose up -d` + 拷回 `.env` 和 `tls/` 即可完全恢复。

## 八、关键设计决策

### 为什么不直接用 Vercel / Railway / Render

- **数据合规**：内部 AI 项目可能涉及客户数据，不能跑在外部 SaaS
- **成本**：内部很多项目流量小但 24h 在线，外部按流量/小时计费不划算
- **内网集成**：用户应用需要直接访问公司 OIDC、内部 DB、内网服务

### 为什么不用 Helm / ArgoCD

- 用户群是工程师 + PM + ops，**写 YAML 是负向 UX**
- 我们要的是"压低门槛"，不是"暴露 K8s 能力"
- Helm 适合 ops 给 ops 用，不适合"我有个 demo 项目想给团队看看"

### 为什么 build-service 用 docker daemon 而不是 Kaniko

- 起步阶段 docker daemon 是免费的；Kaniko 需要 PVC + cache 管理
- 后期扩容到多 build 实例 / K8s 化时再迁，不是 day-1 决策

### 为什么 K3s 而不是 EKS / ACK

- 我们要在自己的 ECS 上跑，托管 K8s 不一定能拉私有 registry / 走内网
- K3s 单 binary、配置简单、控制面 < 1GB，单节点起步合适

### 为什么 SSE 不是 WebSocket

- 部署日志是单向流（server → client），SSE 够用
- SSE 走标准 HTTP，浏览器/curl/中间件兼容性好
- WebSocket 多一层握手 + 自定义协议，没必要

### 为什么每个项目一个 namespace

- 网络策略 / RBAC / 资源配额都能在 namespace 粒度天然隔离
- 一键删项目 = `kubectl delete ns proj-<slug>`，K8s 级联清理所有相关资源
- namespace 数量不是问题（K3s 测过 1000+ 没事）

### 为什么 HMAC state 而不是 cookie state

- OIDC 标准的 state 通常存 cookie；我们的 Web UI 和 Skill 跨端口跨子域，cookie scope 容易踩坑
- HMAC 签名 state 自包含一切信息，不依赖 cookie，stateless 也对 HA 友好

### 为什么 Traefik DaemonSet + hostNetwork

- 不需要外部 LB，每个节点的 :80/:443 都能服务流量，DNS 轮询即可
- ServiceLB 在云 ECS 上拿不到公网 IP（要 LoadBalancer 类型 Service，公有云另外计费）
- hostNetwork = "我就要这台机器的 :80"，配 `NET_BIND_SERVICE` capability 让非 root 进程也能绑

## 十、术语

| 术语 | 意思 |
|---|---|
| **平台节点** | 跑 control-plane + 集群 server 的中心节点（it-iai-k3s-server） |
| **Worker / Agent** | 仅运行用户应用 pod 的 K3s agent 节点 |
| **Skill** | Claude Code 的命令包，本项目的 `skill/` 目录 |
| **Deploy Token** | `vbd_live_*` 前缀的长生命周期 token，主要给 Skill / CI 用 |
| **Manifest** | Skill 扫描得到的项目描述（不是 K8s manifest） |
| **Project Slug** | URL 友好的项目标识，如 `iai-test-project-wj7g` |
| **Visibility** | `org` / `restricted`——决定 SSO 之后是否还要过协作者名单。`public`（完全免 SSO）已于 2026-07 停用，仅历史行仍可能带此值 |
| **Preset** | 命名 CIDR 预设，全局维护，项目从下拉里选 |
