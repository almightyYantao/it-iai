# 爱 AI · 运维手册

> 给负责生产部署的工程师 / SRE。覆盖**备份**、**外置状态**（PG / MinIO / Registry）、**多平台节点 HA**。按需读，不一定一次性全做完。

---

## 阅读地图

按 **收益/工作量** 从高到低排：

| 阶段 | 做什么 | 工作量 | 收益 |
|---|---|---|---|
| **§1 备份** | 配每日 pg_dump + MinIO 同步 + 配置文件加密外存 | 0.5 天 | **必做**。低成本，最坏情况能恢复 |
| **§2 PG 外置** | 数据库搬到 RDS 或独立 ECS | 0.5 天 | 平台节点磁盘坏不丢业务数据 |
| **§3 MinIO 外置** | 对象存储搬到 OSS 或独立 ECS | 0.5 天 | 源码包不丢，可扩容 |
| **§4 Registry 外置** | 镜像仓搬到 ACR 或独立 ECS | 0.5 天 | 节省平台节点磁盘，工人节点拉镜像更快 |
| **§5 多平台节点 + HA** | 平台节点跑两台，前面挂 SLB | 1-2 天 | 控制面单点消除，可滚动升级 |

§2-§4 都依赖 §1 的备份，但彼此独立。§5 强烈建议 **先做完 §2-§4** 再做，否则你只是把一个 stateful 单点变成两个 stateful 单点。

## §1 备份

### 1.1 备份什么

| 数据 | 路径 / 位置 | 优先级 | 频率 |
|---|---|---|---|
| 控制面 Postgres（项目、用户、token、审计、加密 env） | docker volume `it-iai_pgdata` | **必备份** | 每天 |
| **用户 Postgres（业务数据库）** | docker volume `it-iai_userpgdata` | **必备份** | 每天 |
| MinIO（平台源码 tarball + 用户应用 bucket + **用户 SQLite 数据**） | docker volume `it-iai_miniodata` | **必备份** | 每天 |
| Redis 持久化（ACL 用户表 + 用户应用 cache） | docker volume `it-iai_redisdata` | 中 | 每周 |
| Registry（镜像层） | docker volume `it-iai_registrydata` | 中 | 可选（理论可重建） |
| `.env`（含 `CP_KEK_BASE64` 根密钥 + 各服务 admin 密码） | `/opt/it-iai/.env` | **必备份** | 每次改动后 |
| TLS 证书 + 私钥 | `/opt/it-iai/tls/` | **必备份** | 续签时 |
| K3s server token | `/var/lib/rancher/k3s/server/node-token` | 中 | worker 加入时用 |
| K3s manifests | `/var/lib/rancher/k3s/server/manifests/` | 中 | 改 HelmChartConfig 时 |

⚠️ **`.env` 千万不能丢**——`CP_KEK_BASE64` 是控制面 DB 里加密字段（Deploy Token + 项目 env）的根密钥，丢了所有 token / DATABASE_URL / S3 凭据解不开。

⚠️ **`it-iai_userpgdata` 是业务数据**——存的是用户应用的 Postgres 内容（订单、用户表、文档等等）。丢了等于丢业务数据。和控制面 PG 同等优先级备份。

⚠️ **用户应用的 SQLite 数据也躺在 `it-iai_miniodata` 里**——`needs.sqlite=true` 的项目，Litestream sidecar 把 `/data/app.db` 持续同步到项目自家 MinIO bucket（key 名 `app.db`）。所以**不需要为 SQLite 单独配备份**，把 `it-iai_miniodata` 备份做好就行。pod 内的 `emptyDir` 是临时副本，丢了也无所谓——下次启动 init container 会从 bucket 拉最新快照恢复。

### 1.2 一键备份脚本

把下面这个保存为 `/opt/it-iai/deploy/backup.sh`：

```bash
#!/usr/bin/env bash
# 每日运维备份。建议放 cron。
set -euo pipefail

REPO_ROOT="${REPO_ROOT:-/opt/it-iai}"
DEST="${BACKUP_DEST:-/var/backups/it-iai}/$(date +%F)"
RETENTION_DAYS="${RETENTION_DAYS:-7}"

mkdir -p "$DEST"
cd "$REPO_ROOT"

# 1. 控制面 Postgres — pg_dump 走 docker exec
echo "[$(date +%T)] dumping control-plane postgres..."
docker compose exec -T postgres \
  pg_dump -U vibedeploy -d vibedeploy --no-owner --clean --if-exists \
  | gzip > "$DEST/postgres.sql.gz"

# 2. 用户 Postgres — 业务数据库。pg_dumpall 一把抓所有 proj_* DB
echo "[$(date +%T)] dumping user postgres (all proj_* DBs)..."
docker compose exec -T user-postgres \
  pg_dumpall -U iaiadmin --clean --if-exists \
  | gzip > "$DEST/user-postgres.sql.gz"

# 3. MinIO — 直接 tar volume（一致性可以接受，少量未完成的 multipart 不影响）
#    含平台 source 桶 + 用户应用 proj-* 桶
echo "[$(date +%T)] tarring minio volume..."
tar -czf "$DEST/minio-data.tar.gz" \
  -C /var/lib/docker/volumes/it-iai_miniodata/_data .

# 3. .env + TLS — 这两个体积小，每次都打包
echo "[$(date +%T)] copying secrets..."
cp .env "$DEST/.env"
if [[ -d tls ]]; then
  tar -czf "$DEST/tls.tar.gz" -C . tls/
fi

# 4. K3s 元数据
echo "[$(date +%T)] saving k3s metadata..."
[[ -f /var/lib/rancher/k3s/server/node-token ]] && \
  cp /var/lib/rancher/k3s/server/node-token "$DEST/k3s-node-token"
[[ -d /var/lib/rancher/k3s/server/manifests ]] && \
  tar -czf "$DEST/k3s-manifests.tar.gz" -C /var/lib/rancher/k3s/server manifests/

# 5. 体积检查 + 保留 N 天
du -sh "$DEST" | awk '{print "  size: "$1}'
find "$(dirname "$DEST")" -maxdepth 1 -type d -mtime "+$RETENTION_DAYS" \
  -exec rm -rf {} + 2>/dev/null || true

echo "[$(date +%T)] done → $DEST"
```

挂 cron：

```bash
sudo chmod +x /opt/it-iai/deploy/backup.sh
echo "0 3 * * * /opt/it-iai/deploy/backup.sh >> /var/log/it-iai-backup.log 2>&1" \
  | sudo crontab -
```

### 1.3 异地存储（关键）

上面只是落到**本机** `/var/backups/`，磁盘坏了一锅端。**强烈建议**把备份目录推到对象存储。最简单的接 OSS：

```bash
# 装 ossutil 之后
ossutil cp -r /var/backups/it-iai/$(date +%F)/ oss://lb-iai-backups/$(date +%F)/ --update
```

把这条加到 `backup.sh` 末尾。生命周期规则在 OSS 控制台配（保留 30 天）。

### 1.4 演练恢复

**强制建议**：每个月跑一次恢复演练，否则不知道备份能不能用。

```bash
# 1. 在备机或测试环境
# 2. 假装从备份恢复 PG
docker compose exec -T postgres dropdb -U vibedeploy --if-exists vibedeploy_restore
docker compose exec -T postgres createdb -U vibedeploy vibedeploy_restore
zcat /path/to/backup/postgres.sql.gz \
  | docker compose exec -T postgres psql -U vibedeploy -d vibedeploy_restore

# 3. 简单 sanity check
docker compose exec -T postgres psql -U vibedeploy -d vibedeploy_restore \
  -c "SELECT count(*) FROM projects;"
```

## §2 PG 外置（搬到 RDS / 独立 ECS）

### 2.1 为什么

- 平台节点磁盘坏 → DB 没了 → 所有项目元数据丢
- DB 占 IO，跟 control-plane / build-service 抢资源
- 想做控制面 HA，DB 必须先外置

### 2.2 两条路径

| 选项 | 优点 | 缺点 |
|---|---|---|
| **阿里云 RDS PostgreSQL** | 全托管，自动备份 / 高可用 / 监控 | 月成本（5GB 入门版几十块） |
| **自建独立 ECS + Postgres** | 0 月费（除 ECS 费用） | 你要自己管备份 / 监控 / 升级 |

新项目 / 小团队 → 不犹豫选 RDS。极度抠成本 → 自建。

### 2.3 RDS 迁移步骤

```bash
# === 在 RDS 控制台 ===
# 1. 创建实例：PostgreSQL 16，存储 ≥ 20GB，VPC 跟平台节点同 VPC
# 2. 加白名单：把平台节点内网 IP 加进 RDS 的白名单
# 3. 创建账号 + 数据库 vibedeploy
# 4. 拿到内网连接串，类似:
#    postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/vibedeploy

# === 在平台节点 ===
# 5. 停掉 control-plane + build-service（停止写入）
cd /opt/it-iai
sudo docker compose stop control-plane build-service

# 6. 全量 dump
sudo docker compose exec -T postgres \
  pg_dump -U vibedeploy -d vibedeploy --no-owner --clean --if-exists \
  > /tmp/pg-dump.sql

# 7. 灌进 RDS（在平台节点装 psql 客户端，或者用 docker run 一次性容器）
psql "postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/postgres" \
  -c "CREATE DATABASE vibedeploy;" || true
psql "postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/vibedeploy" \
  < /tmp/pg-dump.sql

# 8. 改 .env，把 CP_DATABASE_URL 指向 RDS
sudo sed -i.bak 's|^CP_DATABASE_URL=.*|CP_DATABASE_URL=postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/vibedeploy?sslmode=disable|' \
  /opt/it-iai/.env

# 9. 启动 control-plane，验证
sudo docker compose up -d control-plane
sudo docker compose logs -f control-plane   # 看到 "control-plane listening on :8080" 就 OK

# 10. 跑通后，停掉内置 PG 容器（先停，留 7 天观察期再删 volume）
sudo docker compose stop postgres
# 7 天后没问题再 docker volume rm it-iai_pgdata
```

### 2.4 验证清单

- [ ] Web 后台能登录
- [ ] 项目列表能拉出来
- [ ] 推一个 demo 项目能跑通完整流程（首次创建项目要写库）
- [ ] 审计日志能看到刚才的操作
- [ ] 重启 control-plane 容器后还能用

## §3 MinIO 外置（搬到 OSS / 独立 MinIO）

### 3.1 为什么

- MinIO 存的是**源码 tarball**，万一丢了，老 deployment 的源码就回溯不了（部署本身还在 K3s 上跑，不影响线上服务）
- OSS 在阿里云上几乎免费（按量计费 + accelerator），冷数据放 OSS 性价比远高于 ECS 磁盘

### 3.2 两条路径

| 选项 | 优点 | 缺点 |
|---|---|---|
| **阿里云 OSS** | 几乎免费，原生 S3 兼容 | 配置稍微多（access key + endpoint） |
| **独立 ECS 跑 MinIO** | 简单，跟现在一模一样的 API | 还是你自己运维 |

### 3.3 OSS 迁移步骤

```bash
# === OSS 控制台 ===
# 1. 创建 bucket：vibedeploy-source（私有读写、同区域）
# 2. 在 RAM 控制台创建子账号，授 AliyunOSSFullAccess（或更细粒度只授该 bucket）
# 3. 拿 AccessKeyId / AccessKeySecret

# === 平台节点 ===
# 4. 装 mc 客户端配置内置 MinIO + OSS
sudo docker run --rm --network it-iai_default \
  minio/mc:latest \
  alias set internal http://minio:9000 vibedeploy vibedeploypw

sudo docker run --rm \
  -e MC_HOST_oss="https://<accesskeyid>:<accesskeysecret>@oss-cn-hongkong.aliyuncs.com" \
  minio/mc:latest \
  alias set oss https://oss-cn-hongkong.aliyuncs.com <accesskeyid> <accesskeysecret>

# 5. 同步全部对象（首次全量，后续增量）
sudo docker run --rm --network it-iai_default \
  -e MC_HOST_oss="https://<accesskeyid>:<accesskeysecret>@oss-cn-hongkong.aliyuncs.com" \
  minio/mc:latest \
  mirror --overwrite internal/vibedeploy-source oss/lb-iai-source-bucket

# 6. 改 .env
sudo tee -a /opt/it-iai/.env <<EOF
CP_S3_ENDPOINT=oss-cn-hongkong-internal.aliyuncs.com:80
CP_S3_PUBLIC_ENDPOINT=oss-cn-hongkong.aliyuncs.com
CP_S3_REGION=cn-hongkong
CP_S3_ACCESS_KEY=<accesskeyid>
CP_S3_SECRET_KEY=<accesskeysecret>
CP_S3_BUCKET_SOURCE=lb-iai-source-bucket
CP_S3_USE_SSL=false
CP_S3_PUBLIC_USE_SSL=true
EOF
# 注：以上是追加，要去文件里把旧的 CP_S3_* 同名行删掉

# 7. 重启
sudo docker compose up -d --build control-plane build-service

# 8. 验证：在 Skill 推一个新项目，看 build 日志是否能从 OSS 下载源码
```

### 3.4 验证清单

- [ ] 新 push 一个项目，看构建日志有「download source from ...oss...」之类的字样
- [ ] 项目能成功部署到 K3s
- [ ] 老项目（OSS 上有旧 tarball）能重新部署

### 3.5 上传入口：预签名 URL 的三方耦合

开发机上传源码走的是**服务端签发的预签名 URL**，客户端（Skill）只是 PUT 到拿到的地址，不关心指向哪。所以换上传入口不需要动 Skill，但下面三处必须一致，改一处就要同步改：

| 位置 | 值 | 作用 |
|---|---|---|
| `.env` `CP_S3_PUBLIC_ENDPOINT` | admin 域名 | 预签名 URL 的 host，**同时是 SigV4 签名的一部分** |
| `.env` `CP_S3_PUBLIC_USE_SSL` | `true` | 决定生成 `https://` 还是 `http://` |
| `web/nginx.conf` 的 `location /<bucket>/` | 与 `CP_S3_BUCKET_SOURCE` 同名 | 把该前缀反代到 `minio:9000` |

为什么要经 nginx：MinIO 的 9000 端口不对开发机开放（云安全组关闭），而 443 一定通。

三个容易踩的点：

1. **反代不能改 Host、不能改路径。** SigV4 把 Host 头和 URI 路径都签进签名，`proxy_set_header Host $host` 必须保留，`proxy_pass` 后面不能带路径（带了就是重写）。任一条不满足，MinIO 返回的是 `SignatureDoesNotMatch`——看起来像凭据错，实际是路由把签名破坏了。
2. **必须 path-style。** 预签名走 `/<bucket>/<key>`（`internal/storage/minio.go` 里显式设了 `BucketLookupPath`）。virtual-host style 会生成 `bucket.admin.…` 这种 host，DNS 和上面那个 location 都对不上。
3. **`client_max_body_size` 要放开。** nginx 默认 1MB，源码包动辄几十 MB，不改会直接 413。顺带 `proxy_request_buffering off`，否则整包先落 nginx 磁盘再转发。

改完的验证必须**从平台外的机器**做一次真实上传——在宿主上测会因为走 loopback 而掩盖问题：

```bash
# 拿一个预签名 URL 并直接 PUT
resp=$(curl -sS -X POST "$API/v1/projects/<slug>/deployments" -H "Authorization: Bearer $TOK" \
  -H 'Content-Type: application/json' -d '{"manifest":{"name":"x","port":3000}}')
curl -sS -X PUT --data-binary @some.tar.zst -H 'Content-Type: application/zstd' \
  "$(echo "$resp" | jq -r .upload_url)" -w '\nhttp=%{http_code}\n'
# 期望 200；403 + SignatureDoesNotMatch = 反代改了 Host 或路径
```

## §4 Registry 外置（搬到 ACR / 独立 Registry）

### 4.1 为什么

- Registry 占的磁盘最快（每个项目镜像 50-200MB，每次部署一个新 layer 集合）
- 平台节点磁盘不大的话，前几个月就会满
- ACR 几乎免费（按量计费），workers 拉镜像更快（同 region 内网）

### 4.2 ACR 迁移步骤

```bash
# === ACR 控制台 ===
# 1. 创建企业版（或个人版）实例，开 VPC 接入
# 2. 创建命名空间 lb-iai
# 3. 设置免密拉取（通过 VPC 内网）

# === 平台节点 ===
# 4. 列出所有现有镜像并复制到 ACR
images=$(docker exec it-iai-registry-1 cat /var/lib/registry/docker/registry/v2/repositories \
  -ls 2>/dev/null || echo "")
# 实际上更直接的方式是用 skopeo（复制带 tag 的整套）：
for repo in $(curl -s http://localhost:5001/v2/_catalog | jq -r '.repositories[]'); do
  for tag in $(curl -s "http://localhost:5001/v2/$repo/tags/list" | jq -r '.tags[]?'); do
    skopeo copy --src-tls-verify=false \
      docker://localhost:5001/$repo:$tag \
      docker://lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai/$repo:$tag
  done
done

# 5. 改 .env
sudo sed -i.bak \
  -e 's|^CP_REGISTRY_HOST=.*|CP_REGISTRY_HOST=lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai|' \
  -e 's|^CP_REGISTRY_HOST_FROM_K3D=.*|CP_REGISTRY_HOST_FROM_K3D=lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai|' \
  /opt/it-iai/.env

# 6. 改每台 worker 的 /etc/rancher/k3s/registries.yaml，把 mirror 指向 ACR
# （或者直接让 image tag 用 ACR 域名，K3s 默认就能拉）

# 7. 重启 control-plane + build-service
sudo docker compose up -d --build control-plane build-service

# 8. 重启每台 worker 的 k3s-agent 让 registries.yaml 生效
ssh worker-N "sudo systemctl restart k3s-agent"

# 9. 验证：推一个新项目，看 K3s 是否能从 ACR 拉到镜像
```

### 4.3 验证清单

- [ ] 新推的项目 pod 状态变成 Running（镜像拉成功）
- [ ] worker 上 `crictl images` 能看到 `lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/...` 的条目
- [ ] 老项目（镜像在老 registry 上）重新部署也 OK（已经复制过去）

## §5 多平台节点 + HA

**做这一步之前**：§2 §3 §4 全部完成。否则两个平台节点会各自抢 state 容器，乱套。

### 5.1 架构目标

```
                ┌─── 阿里云 SLB ───┐
                │  *.example.com   │
                │  admin / auth    │
                └────────┬─────────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
        ┌──────────┐          ┌──────────┐
        │ platform │          │ platform │  (active/active)
        │  node 1  │          │  node 2  │
        └────┬─────┘          └────┬─────┘
             │                     │
             └──────┬──────────────┘
                    │ 共用：
                    ▼
        ┌────────────────────────────┐
        │  RDS PG                    │
        │  OSS                       │
        │  ACR                       │
        │  K3s server HA（3 etcd） │
        └────────────────────────────┘
```

### 5.2 第二台平台节点

```bash
# 在第二台 ECS 上：
git clone <repo> /opt/it-iai
cd /opt/it-iai

# 把第一台的 .env 拷过来（KEK 必须一致，否则解不了同一份 DB 里的加密字段）
scp platform-1:/opt/it-iai/.env ./

# 跑 docker-compose 但 NOT 跑 K3s server（K3s 单独处理，见 5.3）
sudo SKIP_K3S=1 deploy/install-platform.sh   # （需要在 install-platform.sh 里支持这个标志）
# 或者手动:
sudo docker compose up -d
```

### 5.3 K3s server HA

K3s 单 server 升级到 3-server etcd 模式：

```bash
# 第一台（已有的）现在用的是 SQLite 后端，要先切换到 embedded etcd
# 这步是破坏性的，做完整备份再来：

# 1. 备份 + 关掉 worker（让 server 短暂不可用）
sudo /usr/local/bin/k3s etcd-snapshot save --name pre-ha-migration

# 2. 重启 server 切到 etcd
sudo systemctl stop k3s
sudo curl -sfL https://get.k3s.io | \
  INSTALL_K3S_EXEC="server --cluster-init --node-taint CriticalAddonsOnly=true:NoExecute" \
  sh -s -

# 3. 在第二台加入 server cluster
sudo curl -sfL https://get.k3s.io | \
  K3S_TOKEN="<token>" \
  K3S_URL="https://<platform-1>:6443" \
  INSTALL_K3S_EXEC="server --server https://<platform-1>:6443 --node-taint CriticalAddonsOnly=true:NoExecute" \
  sh -s -

# 4. 第三台（如果有）同上
# 5. 验证
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get --raw /api/v1/namespaces/kube-system/endpoints/kube-controller-manager -o yaml
```

⚠️ etcd HA 必须 **奇数** server（1, 3, 5）。2 server 比 1 server 更脆弱——任何一个挂了 etcd 就 lose quorum。

### 5.4 SLB

| 入口 | SLB 监听 | 后端 |
|---|---|---|
| `*.example.com:443` | 443 TCP | 所有 platform 节点 :443 |
| `admin.example.com:443` | 443 TCP | 所有 platform 节点 :443 |
| `auth.example.com:443` | 443 TCP | 所有 platform 节点 :443 |
| API 内部（control-plane） | TCP 8080 + 健康检查 `/healthz` | 所有 platform 节点 :8080 |

DNS 全部指向 SLB 的 VIP。

## §6 TLS：通配证书 vs 按项目签发

平台支持两种 TLS 模式，**任选一种**（也可以并存：通配管 admin/auth 平台子域、按项目签发管业务 app）。

### 6.1 模式 A：通配证书（DNS-01 / 自带证书）

一张 `*.<base-domain>` 通配证书覆盖所有 app 子域，**适合**：

- 已经有自动续签的通配证书（如 acme.sh + 阿里云 DNS）
- 部署的 app 数量大、Let's Encrypt HTTP-01 限额（50/周/域名）会撞
- 网络环境复杂、:80 不一定公网可达

操作：把 `*.crt` + `*.key` 放到 `/opt/it-iai/tls/`，然后 `/opt/it-iai/deploy/install-tls.sh`。续期换文件后重跑同一个脚本。

**通配符只匹配一级 label。** base domain 是 `iai.longbridge-inc.com` 的话，证书 SAN 必须是 `*.iai.longbridge-inc.com`；`*.longbridge-inc.com` 只覆盖到 `iai.longbridge-inc.com` 本身，所有 app 子域都不匹配。脚本会打印 `cert covers: ...`，装之前对一眼。

**换证书时显式传 `--cert` / `--key`。** 不传参数时脚本按 `/opt/it-iai/tls/*.crt` → `*.pem` 的顺序 glob 第一个匹配项，目录里有旧域名的残留文件时会挑错。旧证书建议移到 `/opt/it-iai/tls/archive-<域名>-<日期>/`。

**脚本第 3 步是整体覆盖写 `traefik-config.yaml`，不是 merge patch。** 任何手工加进集群、但没回写到脚本里的 Traefik 配置，都会在下次换证书时被静默抹掉。`providers.kubernetesCRD.allowCrossNamespace` 就踩过一次：它是 per-project path rule（项目 API token）需要的，当初手工 apply 上去、没回写脚本，换证书时差点把所有带 rule 项目的 token 鉴权带下线。给 Traefik 加配置请改 `install-tls.sh` 里那段 heredoc，别直接改集群。

验证（换证书后跑一遍）：

```bash
# 平台节点上：按 SNI 分别看实际吐出来的证书
for h in <随便一个不存在的slug>.iai.longbridge-inc.com admin.iai.longbridge-inc.com; do
  printf "%-46s " "$h"
  echo | openssl s_client -connect 127.0.0.1:443 -servername "$h" 2>/dev/null \
    | openssl x509 -noout -subject -enddate | tr "\n" " "; echo
done

# 确认 allowCrossNamespace 没被抹掉
grep -A2 "providers:" /var/lib/rancher/k3s/server/manifests/traefik-config.yaml

# 确认 Traefik 没被重启（AGE 应该还是换证书之前的）
k3s kubectl -n kube-system get pods -l app.kubernetes.io/name=traefik
```

不存在的 slug 应该吐通配证书（走 TLSStore/default 兜底），`admin` / `auth` 应该吐它们自己 cert-manager 签的证书 —— 显式 `tls:` 段优先级高于 TLSStore。

**Let's Encrypt 签的通配证书只有 90 天。** 自带证书模式下没有自动续期，到期即全站证书失效。用 LE 通配的话，配 acme.sh + 阿里云 DNS-01 自动续签，并在续签 hook 里重跑 `install-tls.sh`；或者干脆走模式 B。

### 6.2 模式 B：按项目按需签发（HTTP-01）

cert-manager 安装一次，业务方在 **项目设置 → HTTPS** 自助开启，每个 app 拿到独立证书并自动续期，**适合**：

- 没有 DNS API / 不想接入 DNS provider
- app 数量少（每个域名独立占一个 LE 名额）
- 业务方需要灵活控制要不要 HTTPS

第一次安装：

```bash
sudo ACME_EMAIL=you@example.com /opt/it-iai/deploy/install-cert-manager.sh
```

脚本创建两个 ClusterIssuer：

| 名称 | 用途 | 限额 |
|---|---|---|
| `letsencrypt-prod` | 默认，签真证书 | 50/周/域名 |
| `letsencrypt-staging` | 测试，**不被浏览器信任** | 高 |

控制面默认用 `letsencrypt-prod`。要切到 staging 验证流程，改 `.env`：

```bash
CP_TLS_CLUSTER_ISSUER=letsencrypt-staging
docker compose up -d control-plane
```

### 6.3 单个项目开 HTTPS 的流程

1. 业务方在 Web 进入项目 → **设置 → HTTPS** → 勾选「为本项目启用 HTTPS」→ 保存
2. control-plane 给 Ingress 加上 `cert-manager.io/cluster-issuer` 注解 + `tls:` 段
3. cert-manager 创建 `Certificate` 资源，对每个域名跑 HTTP-01 挑战
4. 约 30 秒后证书写入 `iai-tls-<slug>` Secret，Traefik 自动加载

排查：

```bash
sudo k3s kubectl -n proj-<slug> get certificate
sudo k3s kubectl -n proj-<slug> describe certificate iai-tls-<slug>
sudo k3s kubectl -n cert-manager logs deploy/cert-manager -f
```

### 6.4 HTTP-01 的硬性前置

- `<slug>.<base-domain>` 以及所有自定义域名，都必须解析到平台公网 IP
- :80 **必须**公网可达 —— Let's Encrypt 的验证服务从外网过来，**绕过** VPN、IP 白名单
- 撞限额时换 staging 调试，调通再切回 prod

### 6.4.1 云厂 hairpin-NAT（已被 install-cert-manager.sh 自动绕过）

阿里云 / 腾讯云的 ECS **不允许通过自己的公网 IP 回到自己**（数据包出去再进来会被丢）。cert-manager 在通知 LE 之前要做自己的 self-check：从 cert-manager pod 内部 curl `http://<host>/.well-known/acme-challenge/...`。如果 host 解析到公网 IP，self-check 永远 `context deadline exceeded`，证书一直停在 `pending`。

`install-cert-manager.sh` 跑完会自动写一条 `coredns-custom` 的 CoreDNS 重写规则：**集群内** 解析 `*.<CP_APP_BASE_DOMAIN>` 直接返回平台节点的内网 IP，绕开公网回环。**集群外**（LE 验证、浏览器、curl）走公网 DNS 不受影响。

如果是已存在的旧集群，cert-manager 装好后跑这条手动补一次：

```bash
PLATFORM_IP=$(k3s kubectl get node -o jsonpath='{.items[0].status.addresses[?(@.type=="InternalIP")].address}')
BASE_DOMAIN=$(awk -F= '$1=="CP_APP_BASE_DOMAIN"{sub(/^[^=]*=/,""); print}' /opt/it-iai/.env)
cat <<YAML | k3s kubectl apply -f -
apiVersion: v1
kind: ConfigMap
metadata: { name: coredns-custom, namespace: kube-system }
data:
  iai-loopback.override: |
    template IN A ${BASE_DOMAIN} {
      match ^[^.]+\.${BASE_DOMAIN//./\\.}\.\$
      answer "{{ .Name }} 60 IN A ${PLATFORM_IP}"
      fallthrough
    }
YAML
k3s kubectl -n kube-system rollout restart deploy coredns
```

验证：`k3s kubectl -n cert-manager exec deploy/cert-manager -- nslookup admin.<base-domain>` 应该返回**内网 IP**，不是公网。

### 6.5 模式切换

A → B：不用动通配证（仍兜底 TLSStore），跑 `install-cert-manager.sh`，业务方按需开 HTTPS 即可。

B → A：把所有项目设置里的 HTTPS 关掉（control-plane 会移除 `tls:` 段，cert-manager 会回收 Certificate），然后跑 `install-tls.sh` 装通配。

### 6.6 admin / auth 子域自己怎么走

`install-admin-ui-tls.sh` 和 `install-oauth2-proxy.sh` 装的 `admin.<domain>` / `auth.<domain>` 两条 Ingress，行为按以下顺序自动选择：

1. **环境变量 `CLUSTER_ISSUER`** 显式指定（如 `letsencrypt-staging` 或 `none`）
2. 否则探测集群里 `letsencrypt-prod` / `letsencrypt-staging` 任一存在 → 用 cert-manager 给两个 host 各签独立证书（secret 名 `admin-ui-tls` / `oauth2-proxy-tls`）
3. 都没有 → 退回通配 TLSStore（旧行为）

所以装完 cert-manager 之后，**重跑一次这两个脚本** 即可把 admin / auth 也搬到 cert-manager 自动续期：

```bash
sudo bash deploy/install-admin-ui-tls.sh
sudo bash deploy/install-oauth2-proxy.sh
```

要临时退回通配（cert-manager 装在那但你这俩 host 还不想走它）：`CLUSTER_ISSUER=none sudo bash deploy/install-admin-ui-tls.sh`。

## §7 集群 / DB 对账（drift 巡检）

平台的「真相」分在两处：DB 的 `projects` 表和集群里的 `proj-*` namespace。正常情况下两边一一对应，因为所有列表查询、健康 reconciler、启动 ingress sweep 都以 `deleted_at IS NULL` 的 DB 行为准。

两边一旦不一致，**多出来的 namespace 是最危险的那种**：它在跑、在对外服务，但平台完全看不见它——不出现在 UI、健康状态不再纠偏、TLS / CIDR 策略变更不再下发、owner 调管理接口拿 404、连删除接口都走不通（`requireProjectAccess` 先按 slug 查活项目，查不到直接 404），只能用 kubectl 手工处理。

### 7.1 对账命令

```bash
kubectl get ns --no-headers -o custom-columns=":metadata.name" \
  | grep '^proj-' | sed 's/^proj-//' | sort > /tmp/ns.txt

docker exec it-iai-postgres-1 psql -U vibedeploy -d vibedeploy -tAc \
  "SELECT slug FROM projects WHERE deleted_at IS NULL ORDER BY 1" | sort > /tmp/db.txt

echo "集群有 / DB 无（孤儿活负载，重点）:"; comm -23 /tmp/ns.txt /tmp/db.txt
echo "DB 有 / 集群无（未部署或丢失）:";     comm -13 /tmp/ns.txt /tmp/db.txt
```

### 7.2 孤儿负载怎么处置

先判断这个项目**应不应该活着**：

```bash
docker exec it-iai-postgres-1 psql -U vibedeploy -d vibedeploy -P pager=off -c "
SELECT p.slug, u.email AS owner, p.status, p.deleted_at, d.trigger_type, d.triggered_by
FROM projects p LEFT JOIN users u ON u.id = p.owner_id
LEFT JOIN deployments d ON d.project_id = p.id AND d.status = 'running'
WHERE p.slug = '<slug>';"
```

- **该活** → 清掉墓碑，让它回到平台管辖：
  `UPDATE projects SET deleted_at = NULL, status = 'running' WHERE slug = '<slug>';`
  顺手往 `audit_logs` 补一行说明原因，否则以后没人知道这行为什么被复活过。
- **不该活** → `kubectl delete ns proj-<slug>`，DB 保持软删状态。

### 7.3 什么情况会产生 drift

- **恢复 / 迁移脚本只重建了集群侧，没清 `deleted_at`。** 这是最常见的一种，`trigger_type='restore'` 的 deployment 配上有值的 `deleted_at` 就是这个特征。
- **软删时 namespace 没删干净。** `handleDeleteProject` 里 K8s 清理是 best-effort，失败只写 `project.delete.k8s_failed` audit，不阻塞软删。删完项目建议核对一次 audit。
- **代码漏了 `deleted_at` 过滤。** 任何按 `project_id` / `slug` 取项目又不带这个条件的读路径，都可能把已软删项目重新拉起来，详见[技术架构 §3.2](./技术架构.md)。

### 7.4 出站策略巡检（`iai-egress`）

每个项目 namespace 应有一条 `iai-egress` NetworkPolicy，限制 pod 只能访问平台宿主上它该访问的端口（见[技术架构 §3.6](./技术架构.md)）。`Apply` 每次部署会自动重建，所以正常情况下数量应与活项目数一致：

```bash
echo "netpol=$(kubectl get netpol -A --no-headers | grep -c iai-egress)  项目数=$(kubectl get ns --no-headers -o custom-columns=':metadata.name' | grep -c '^proj-')"

# 缺失的命名空间
comm -23 \
  <(kubectl get ns --no-headers -o custom-columns=':metadata.name' | grep '^proj-' | sort) \
  <(kubectl get netpol -A --no-headers | awk '$2=="iai-egress"{print $1}' | sort)
```

验证是否真的生效**必须用长驻 pod**——kube-router 在 pod 创建后才编程规则，短命 pod 会在规则生效前跑完，给出假阴性：

```bash
ns=proj-<slug>
kubectl run npv -n $ns --image=curlimages/curl:8.5.0 --restart=Never --command -- sleep 300
kubectl wait --for=condition=Ready pod/npv -n $ns --timeout=120s && sleep 45
kubectl exec -n $ns npv -- sh -c '
  for hp in <PLATFORM_IP>:5001 <PLATFORM_IP>:5432 <PLATFORM_IP>:8080; do
    printf "%-22s" "$hp(应 BLOCKED)"; nc -z -w4 ${hp%:*} ${hp#*:} && echo OPEN || echo BLOCKED; done
  for hp in <PLATFORM_IP>:5433 <PLATFORM_IP>:6379 <PLATFORM_IP>:9000; do
    printf "%-22s" "$hp(应 OPEN)"; nc -z -w4 ${hp%:*} ${hp#*:} && echo OPEN || echo BLOCKED; done'
kubectl delete pod npv -n $ns --wait=false
```

带 Litestream 的项目（pod 里有 `litestream` sidecar）依赖 MinIO 的 9000，改动这条策略后要回看 sidecar 日志确认仍有 `wal segment written`。

### 7.5 顺带该核对的残留

软删**不级联**，所以这些行会留下来：

```sql
-- domains.hostname 是全表 UNIQUE，软删不释放 → hostname 被永久占用
SELECT p.slug, d.hostname FROM domains d JOIN projects p ON p.id = d.project_id
WHERE p.deleted_at IS NOT NULL;

-- project_path_rules 的 ON DELETE CASCADE 不会因软删触发
SELECT p.slug, r.path_prefix, r.mode FROM project_path_rules r
JOIN projects p ON p.id = r.project_id WHERE p.deleted_at IS NOT NULL;

-- 残留的 api_token_hash（不可用——host→project 查找带 deleted_at 过滤，
-- 但事件复盘时最好归零）
SELECT slug, api_token_prefix FROM projects
WHERE deleted_at IS NOT NULL AND api_token_hash IS NOT NULL;
```

`projects.slug` 同样是全表 UNIQUE 且软删不释放：`SlugAvailable` 只看活项目会说「可用」，实际 INSERT 会撞唯一约束。**要收回一个已删的名字重建，必须硬删那一行**，但硬删会连带影响 `audit_logs.project_id` 关联——合规上要留痕就换个 slug。

S3 bucket 是**故意保留**的（`provision/s3.go` 只删 user + policy），确认无数据后手工 `mc rb --force`。

## §8 凭据轮换

### 8.1 KEK（`CP_KEK_BASE64`）

`project_env` 的密文全部由 KEK 加密、并绑定 `(project_id, key)` 作为 AAD。换 KEK 必须重写全部行，用 `cmd/rekey-env`：

```bash
cd /opt/it-iai
# 0. 先备份控制面 DB —— 这一步会重写 project_env 的每一行
docker exec it-iai-postgres-1 pg_dump -U <cp_user> -d vibedeploy | zstd -o /root/cp-db-before-rekey.sql.zst
cp -a .env /root/env.before-rekey && chmod 600 /root/env.before-rekey

NEW=$(openssl rand -base64 32)
set -a; . ./.env; set +a
# .env 里的 host 是 compose 服务名，从宿主跑要换成映射端口
DSN="postgres://<user>:<pass>@127.0.0.1:5432/vibedeploy?sslmode=disable"

# 1. 先 dry-run：应报 "to migrate: N   unreadable: 0"
rekey-env --dsn "$DSN" --old-kek "$CP_KEK_BASE64" --new-kek "$NEW" --dry-run
# 2. 真实执行，结尾必须出现 "post-migration verify: all rows decrypt under new KEK + AAD"
rekey-env --dsn "$DSN" --old-kek "$CP_KEK_BASE64" --new-kek "$NEW"
# 3. 换 .env，重启 control-plane（在这之前它读不了刚被重写的行）
sed -i "s|^CP_KEK_BASE64=.*|CP_KEK_BASE64=$NEW|" .env
docker compose up -d control-plane web
```

`unreadable > 0` 时工具会拒绝执行——有行既不能用新 KEK+AAD 读、也不能用旧 KEK 读，属于损坏或第三把钥匙，必须先查清楚，不允许半迁移。

**验证不能只看 healthz。** control-plane 启动时不解密 env，要触发一次真实部署才碰得到解密路径（`GetProjectEnv` 在 needs 判断之前无条件执行，失败会以 `env_decrypt` 让部署失败）：

```sql
-- 复用现役镜像的只读重部署，不动任何凭据
INSERT INTO deployments (project_id, trigger_type, triggered_by, status, image_tag, manifest, queued_at)
SELECT p.id,'kek-verify','ops','pushing', d.image_tag, p.manifest, now()
FROM projects p JOIN deployments d ON d.project_id=p.id AND d.status='running'
WHERE p.slug='<某个有 env 的项目>' RETURNING id;
```

### 8.2 平台级凭据

涉及控制面 DB 用户、user-postgres 管理员、Redis `default` 用户、MinIO root。顺序固定为**先改后端 → 再改配置 → 最后重启消费方**，反过来会让 control-plane 拿着新配置连不上旧后端而起不来。

| 凭据 | 后端怎么改 | 配置在哪 |
|---|---|---|
| 控制面 DB 用户 | `ALTER USER` on `it-iai-postgres-1` | `CP_DATABASE_URL`、`BS_DATABASE_URL` |
| user-postgres 管理员 | `ALTER USER` on `it-iai-user-postgres-1` | `CP_USER_PG_ADMIN_PASSWORD`、`CP_USER_PG_ADMIN_URL` |
| Redis `default` | 无需手改，entrypoint 每次启动从 .env 同步 | `CP_USER_REDIS_ADMIN_PASSWORD`、`CP_USER_REDIS_ADMIN_URL` |
| MinIO root | 无需手改，随容器重建生效 | compose `MINIO_ROOT_PASSWORD`、`CP_S3_SECRET_KEY`、`BS_S3_SECRET_KEY` |

四个坑：

1. **`.env` 里有重复键**（`CP_USER_PG_ADMIN_PASSWORD` / `_URL` / `_USER`、`CP_USER_PG_PUBLIC_HOST`、`CP_USER_REDIS_URL_TEMPLATE` 各出现两次）。只改第一处会留下旧值，而读取方通常后者生效。替换后务必回读自检。
2. **compose 里的 `POSTGRES_PASSWORD` 改了不生效**——那只在数据卷初始化时使用，已有实例必须 `ALTER USER`。改 compose 只是为了将来重建时一致。
3. **改 MinIO root 前先确认 IAM 是否加密存储**。无 KMS 的部署里 MinIO 可能用 root 凭据加密 IAM，直接改会让既有 IAM 用户全部失效（所有项目的 S3 账号一起废），那种情况要走 `MINIO_ROOT_USER_OLD` 的重加密流程。检查办法：读一个 `identity.json` 看 `secretKey` 是否明文可见。
   ```bash
   find /var/lib/docker/volumes/it-iai_miniodata/_data/.minio.sys/config/iam/users -name xl.meta | head -1 | xargs strings | grep -o '"secretKey":"[^"]*"' | head -1
   ```
4. **重启 control-plane 必须连带重启 web**。control-plane 容器重建后会换 IP，`it-iai-web-1` 里的 nginx 缓存了旧 upstream，域名侧会持续 502，而宿主直连 `127.0.0.1:8080` 却是 200 —— 很容易误判成后端挂了。

轮换后的验证要覆盖每一套凭据。最省事的办法是让三个 provisioner 各跑一次真实轮换（各挑一个用 pg / redis / s3 的项目，删掉它 `project_env` 里的 sentinel key 再触发部署，见 §7.2 的思路），再加一次真实的源码上传构建来覆盖 build-service 的 `BS_DATABASE_URL` + `BS_S3_SECRET_KEY`。

## 附：迁移顺序总结

```
   现在(单节点 all-in-one)
       │
       ▼
   §1 备份脚本 + 异地存储     ←─ 永远先做这步
       │
       ├─ §2 PG → RDS
       ├─ §3 MinIO → OSS         ←─ 这三步彼此独立，可并行
       └─ §4 Registry → ACR
       │
       ▼
   §5 平台节点 ×2 + SLB + K3s HA
```

每完成一步：跑一次 §1.4 的恢复演练 + §X.4 的验证清单。**不要跳验证**——迁移过程中半个状态在新位置半个在老位置，跑一个真实 deploy 是最快的端到端校验。
