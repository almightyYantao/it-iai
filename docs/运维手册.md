# 爱 AI · 运维手册

> 给负责生产部署的工程师 / SRE。覆盖**备份**、**外置状态**（PG / MinIO / Registry）、**多平台节点 HA**。按需读，不一定一次性全做完。

---

## 阅读地图

按 **收益/工作量** 从高到低排：

| 阶段 | 做什么 | 工作量 | 收益 |
|---|---|---|---|
| **§1 备份** | 配每日 pg_dump + MinIO 同步 + 配置文件加密外存 | 0.5 天 | **必做**。低成本，最坏情况能恢复 |
| **§2 PG 外置** | 数据库搬到 RDS 或独立 ECS | 0.5 天 | 平台节点磁盘坏不丢业务数据 |
| **§3 MinIO 外置** | 对象存储搬到 OSS 或独立 ECS | 0.5 天 | 源码包不丢，可扩容 |
| **§4 Registry 外置** | 镜像仓搬到 ACR 或独立 ECS | 0.5 天 | 节省平台节点磁盘，工人节点拉镜像更快 |
| **§5 多平台节点 + HA** | 平台节点跑两台，前面挂 SLB | 1-2 天 | 控制面单点消除，可滚动升级 |

§2-§4 都依赖 §1 的备份，但彼此独立。§5 强烈建议 **先做完 §2-§4** 再做，否则你只是把一个 stateful 单点变成两个 stateful 单点。

## §1 备份

### 1.1 备份什么

| 数据 | 路径 / 位置 | 优先级 | 频率 |
|---|---|---|---|
| 控制面 Postgres（项目、用户、token、审计、加密 env） | docker volume `it-iai_pgdata` | **必备份** | 每天 |
| **用户 Postgres（业务数据库）** | docker volume `it-iai_userpgdata` | **必备份** | 每天 |
| MinIO（平台源码 tarball + 用户应用 bucket + **用户 SQLite 数据**） | docker volume `it-iai_miniodata` | **必备份** | 每天 |
| Redis 持久化（ACL 用户表 + 用户应用 cache） | docker volume `it-iai_redisdata` | 中 | 每周 |
| Registry（镜像层） | docker volume `it-iai_registrydata` | 中 | 可选（理论可重建） |
| `.env`（含 `CP_KEK_BASE64` 根密钥 + 各服务 admin 密码） | `/opt/it-iai/.env` | **必备份** | 每次改动后 |
| TLS 证书 + 私钥 | `/opt/it-iai/tls/` | **必备份** | 续签时 |
| K3s server token | `/var/lib/rancher/k3s/server/node-token` | 中 | worker 加入时用 |
| K3s manifests | `/var/lib/rancher/k3s/server/manifests/` | 中 | 改 HelmChartConfig 时 |

⚠️ **`.env` 千万不能丢**——`CP_KEK_BASE64` 是控制面 DB 里加密字段（Deploy Token + 项目 env）的根密钥，丢了所有 token / DATABASE_URL / S3 凭据解不开。

⚠️ **`it-iai_userpgdata` 是业务数据**——存的是用户应用的 Postgres 内容（订单、用户表、文档等等）。丢了等于丢业务数据。和控制面 PG 同等优先级备份。

⚠️ **用户应用的 SQLite 数据也躺在 `it-iai_miniodata` 里**——`needs.sqlite=true` 的项目，Litestream sidecar 把 `/data/app.db` 持续同步到项目自家 MinIO bucket（key 名 `app.db`）。所以**不需要为 SQLite 单独配备份**，把 `it-iai_miniodata` 备份做好就行。pod 内的 `emptyDir` 是临时副本，丢了也无所谓——下次启动 init container 会从 bucket 拉最新快照恢复。

### 1.2 一键备份脚本

把下面这个保存为 `/opt/it-iai/deploy/backup.sh`：

```bash
#!/usr/bin/env bash
# 每日运维备份。建议放 cron。
set -euo pipefail

REPO_ROOT="${REPO_ROOT:-/opt/it-iai}"
DEST="${BACKUP_DEST:-/var/backups/it-iai}/$(date +%F)"
RETENTION_DAYS="${RETENTION_DAYS:-7}"

mkdir -p "$DEST"
cd "$REPO_ROOT"

# 1. 控制面 Postgres — pg_dump 走 docker exec
echo "[$(date +%T)] dumping control-plane postgres..."
docker compose exec -T postgres \
  pg_dump -U vibedeploy -d vibedeploy --no-owner --clean --if-exists \
  | gzip > "$DEST/postgres.sql.gz"

# 2. 用户 Postgres — 业务数据库。pg_dumpall 一把抓所有 proj_* DB
echo "[$(date +%T)] dumping user postgres (all proj_* DBs)..."
docker compose exec -T user-postgres \
  pg_dumpall -U iaiadmin --clean --if-exists \
  | gzip > "$DEST/user-postgres.sql.gz"

# 3. MinIO — 直接 tar volume（一致性可以接受，少量未完成的 multipart 不影响）
#    含平台 source 桶 + 用户应用 proj-* 桶
echo "[$(date +%T)] tarring minio volume..."
tar -czf "$DEST/minio-data.tar.gz" \
  -C /var/lib/docker/volumes/it-iai_miniodata/_data .

# 3. .env + TLS — 这两个体积小，每次都打包
echo "[$(date +%T)] copying secrets..."
cp .env "$DEST/.env"
if [[ -d tls ]]; then
  tar -czf "$DEST/tls.tar.gz" -C . tls/
fi

# 4. K3s 元数据
echo "[$(date +%T)] saving k3s metadata..."
[[ -f /var/lib/rancher/k3s/server/node-token ]] && \
  cp /var/lib/rancher/k3s/server/node-token "$DEST/k3s-node-token"
[[ -d /var/lib/rancher/k3s/server/manifests ]] && \
  tar -czf "$DEST/k3s-manifests.tar.gz" -C /var/lib/rancher/k3s/server manifests/

# 5. 体积检查 + 保留 N 天
du -sh "$DEST" | awk '{print "  size: "$1}'
find "$(dirname "$DEST")" -maxdepth 1 -type d -mtime "+$RETENTION_DAYS" \
  -exec rm -rf {} + 2>/dev/null || true

echo "[$(date +%T)] done → $DEST"
```

挂 cron：

```bash
sudo chmod +x /opt/it-iai/deploy/backup.sh
echo "0 3 * * * /opt/it-iai/deploy/backup.sh >> /var/log/it-iai-backup.log 2>&1" \
  | sudo crontab -
```

### 1.3 异地存储（关键）

上面只是落到**本机** `/var/backups/`，磁盘坏了一锅端。**强烈建议**把备份目录推到对象存储。最简单的接 OSS：

```bash
# 装 ossutil 之后
ossutil cp -r /var/backups/it-iai/$(date +%F)/ oss://lb-iai-backups/$(date +%F)/ --update
```

把这条加到 `backup.sh` 末尾。生命周期规则在 OSS 控制台配（保留 30 天）。

### 1.4 演练恢复

**强制建议**：每个月跑一次恢复演练，否则不知道备份能不能用。

```bash
# 1. 在备机或测试环境
# 2. 假装从备份恢复 PG
docker compose exec -T postgres dropdb -U vibedeploy --if-exists vibedeploy_restore
docker compose exec -T postgres createdb -U vibedeploy vibedeploy_restore
zcat /path/to/backup/postgres.sql.gz \
  | docker compose exec -T postgres psql -U vibedeploy -d vibedeploy_restore

# 3. 简单 sanity check
docker compose exec -T postgres psql -U vibedeploy -d vibedeploy_restore \
  -c "SELECT count(*) FROM projects;"
```

## §2 PG 外置（搬到 RDS / 独立 ECS）

### 2.1 为什么

- 平台节点磁盘坏 → DB 没了 → 所有项目元数据丢
- DB 占 IO，跟 control-plane / build-service 抢资源
- 想做控制面 HA，DB 必须先外置

### 2.2 两条路径

| 选项 | 优点 | 缺点 |
|---|---|---|
| **阿里云 RDS PostgreSQL** | 全托管，自动备份 / 高可用 / 监控 | 月成本（5GB 入门版几十块） |
| **自建独立 ECS + Postgres** | 0 月费（除 ECS 费用） | 你要自己管备份 / 监控 / 升级 |

新项目 / 小团队 → 不犹豫选 RDS。极度抠成本 → 自建。

### 2.3 RDS 迁移步骤

```bash
# === 在 RDS 控制台 ===
# 1. 创建实例：PostgreSQL 16，存储 ≥ 20GB，VPC 跟平台节点同 VPC
# 2. 加白名单：把平台节点内网 IP 加进 RDS 的白名单
# 3. 创建账号 + 数据库 vibedeploy
# 4. 拿到内网连接串，类似:
#    postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/vibedeploy

# === 在平台节点 ===
# 5. 停掉 control-plane + build-service（停止写入）
cd /opt/it-iai
sudo docker compose stop control-plane build-service

# 6. 全量 dump
sudo docker compose exec -T postgres \
  pg_dump -U vibedeploy -d vibedeploy --no-owner --clean --if-exists \
  > /tmp/pg-dump.sql

# 7. 灌进 RDS（在平台节点装 psql 客户端，或者用 docker run 一次性容器）
psql "postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/postgres" \
  -c "CREATE DATABASE vibedeploy;" || true
psql "postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/vibedeploy" \
  < /tmp/pg-dump.sql

# 8. 改 .env，把 CP_DATABASE_URL 指向 RDS
sudo sed -i.bak 's|^CP_DATABASE_URL=.*|CP_DATABASE_URL=postgres://vibedeploy:<password>@rm-xxxxx.pg.rds.aliyuncs.com:5432/vibedeploy?sslmode=disable|' \
  /opt/it-iai/.env

# 9. 启动 control-plane，验证
sudo docker compose up -d control-plane
sudo docker compose logs -f control-plane   # 看到 "control-plane listening on :8080" 就 OK

# 10. 跑通后，停掉内置 PG 容器（先停，留 7 天观察期再删 volume）
sudo docker compose stop postgres
# 7 天后没问题再 docker volume rm it-iai_pgdata
```

### 2.4 验证清单

- [ ] Web 后台能登录
- [ ] 项目列表能拉出来
- [ ] 推一个 demo 项目能跑通完整流程（首次创建项目要写库）
- [ ] 审计日志能看到刚才的操作
- [ ] 重启 control-plane 容器后还能用

## §3 MinIO 外置（搬到 OSS / 独立 MinIO）

### 3.1 为什么

- MinIO 存的是**源码 tarball**，万一丢了，老 deployment 的源码就回溯不了（部署本身还在 K3s 上跑，不影响线上服务）
- OSS 在阿里云上几乎免费（按量计费 + accelerator），冷数据放 OSS 性价比远高于 ECS 磁盘

### 3.2 两条路径

| 选项 | 优点 | 缺点 |
|---|---|---|
| **阿里云 OSS** | 几乎免费，原生 S3 兼容 | 配置稍微多（access key + endpoint） |
| **独立 ECS 跑 MinIO** | 简单，跟现在一模一样的 API | 还是你自己运维 |

### 3.3 OSS 迁移步骤

```bash
# === OSS 控制台 ===
# 1. 创建 bucket：vibedeploy-source（私有读写、同区域）
# 2. 在 RAM 控制台创建子账号，授 AliyunOSSFullAccess（或更细粒度只授该 bucket）
# 3. 拿 AccessKeyId / AccessKeySecret

# === 平台节点 ===
# 4. 装 mc 客户端配置内置 MinIO + OSS
sudo docker run --rm --network it-iai_default \
  minio/mc:latest \
  alias set internal http://minio:9000 vibedeploy vibedeploypw

sudo docker run --rm \
  -e MC_HOST_oss="https://<accesskeyid>:<accesskeysecret>@oss-cn-hongkong.aliyuncs.com" \
  minio/mc:latest \
  alias set oss https://oss-cn-hongkong.aliyuncs.com <accesskeyid> <accesskeysecret>

# 5. 同步全部对象（首次全量，后续增量）
sudo docker run --rm --network it-iai_default \
  -e MC_HOST_oss="https://<accesskeyid>:<accesskeysecret>@oss-cn-hongkong.aliyuncs.com" \
  minio/mc:latest \
  mirror --overwrite internal/vibedeploy-source oss/lb-iai-source-bucket

# 6. 改 .env
sudo tee -a /opt/it-iai/.env <<EOF
CP_S3_ENDPOINT=oss-cn-hongkong-internal.aliyuncs.com:80
CP_S3_PUBLIC_ENDPOINT=oss-cn-hongkong.aliyuncs.com
CP_S3_REGION=cn-hongkong
CP_S3_ACCESS_KEY=<accesskeyid>
CP_S3_SECRET_KEY=<accesskeysecret>
CP_S3_BUCKET_SOURCE=lb-iai-source-bucket
CP_S3_USE_SSL=false
CP_S3_PUBLIC_USE_SSL=true
EOF
# 注：以上是追加，要去文件里把旧的 CP_S3_* 同名行删掉

# 7. 重启
sudo docker compose up -d --build control-plane build-service

# 8. 验证：在 Skill 推一个新项目，看 build 日志是否能从 OSS 下载源码
```

### 3.4 验证清单

- [ ] 新 push 一个项目，看构建日志有「download source from ...oss...」之类的字样
- [ ] 项目能成功部署到 K3s
- [ ] 老项目（OSS 上有旧 tarball）能重新部署

## §4 Registry 外置（搬到 ACR / 独立 Registry）

### 4.1 为什么

- Registry 占的磁盘最快（每个项目镜像 50-200MB，每次部署一个新 layer 集合）
- 平台节点磁盘不大的话，前几个月就会满
- ACR 几乎免费（按量计费），workers 拉镜像更快（同 region 内网）

### 4.2 ACR 迁移步骤

```bash
# === ACR 控制台 ===
# 1. 创建企业版（或个人版）实例，开 VPC 接入
# 2. 创建命名空间 lb-iai
# 3. 设置免密拉取（通过 VPC 内网）

# === 平台节点 ===
# 4. 列出所有现有镜像并复制到 ACR
images=$(docker exec it-iai-registry-1 cat /var/lib/registry/docker/registry/v2/repositories \
  -ls 2>/dev/null || echo "")
# 实际上更直接的方式是用 skopeo（复制带 tag 的整套）：
for repo in $(curl -s http://localhost:5001/v2/_catalog | jq -r '.repositories[]'); do
  for tag in $(curl -s "http://localhost:5001/v2/$repo/tags/list" | jq -r '.tags[]?'); do
    skopeo copy --src-tls-verify=false \
      docker://localhost:5001/$repo:$tag \
      docker://lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai/$repo:$tag
  done
done

# 5. 改 .env
sudo sed -i.bak \
  -e 's|^CP_REGISTRY_HOST=.*|CP_REGISTRY_HOST=lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai|' \
  -e 's|^CP_REGISTRY_HOST_FROM_K3D=.*|CP_REGISTRY_HOST_FROM_K3D=lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai|' \
  /opt/it-iai/.env

# 6. 改每台 worker 的 /etc/rancher/k3s/registries.yaml，把 mirror 指向 ACR
# （或者直接让 image tag 用 ACR 域名，K3s 默认就能拉）

# 7. 重启 control-plane + build-service
sudo docker compose up -d --build control-plane build-service

# 8. 重启每台 worker 的 k3s-agent 让 registries.yaml 生效
ssh worker-N "sudo systemctl restart k3s-agent"

# 9. 验证：推一个新项目，看 K3s 是否能从 ACR 拉到镜像
```

### 4.3 验证清单

- [ ] 新推的项目 pod 状态变成 Running（镜像拉成功）
- [ ] worker 上 `crictl images` 能看到 `lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/...` 的条目
- [ ] 老项目（镜像在老 registry 上）重新部署也 OK（已经复制过去）

## §5 多平台节点 + HA

**做这一步之前**：§2 §3 §4 全部完成。否则两个平台节点会各自抢 state 容器，乱套。

### 5.1 架构目标

```
                ┌─── 阿里云 SLB ───┐
                │  *.example.com   │
                │  admin / auth    │
                └────────┬─────────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
        ┌──────────┐          ┌──────────┐
        │ platform │          │ platform │  (active/active)
        │  node 1  │          │  node 2  │
        └────┬─────┘          └────┬─────┘
             │                     │
             └──────┬──────────────┘
                    │ 共用：
                    ▼
        ┌────────────────────────────┐
        │  RDS PG                    │
        │  OSS                       │
        │  ACR                       │
        │  K3s server HA（3 etcd） │
        └────────────────────────────┘
```

### 5.2 第二台平台节点

```bash
# 在第二台 ECS 上：
git clone <repo> /opt/it-iai
cd /opt/it-iai

# 把第一台的 .env 拷过来（KEK 必须一致，否则解不了同一份 DB 里的加密字段）
scp platform-1:/opt/it-iai/.env ./

# 跑 docker-compose 但 NOT 跑 K3s server（K3s 单独处理，见 5.3）
sudo SKIP_K3S=1 deploy/install-platform.sh   # （需要在 install-platform.sh 里支持这个标志）
# 或者手动:
sudo docker compose up -d
```

### 5.3 K3s server HA

K3s 单 server 升级到 3-server etcd 模式：

```bash
# 第一台（已有的）现在用的是 SQLite 后端，要先切换到 embedded etcd
# 这步是破坏性的，做完整备份再来：

# 1. 备份 + 关掉 worker（让 server 短暂不可用）
sudo /usr/local/bin/k3s etcd-snapshot save --name pre-ha-migration

# 2. 重启 server 切到 etcd
sudo systemctl stop k3s
sudo curl -sfL https://get.k3s.io | \
  INSTALL_K3S_EXEC="server --cluster-init --node-taint CriticalAddonsOnly=true:NoExecute" \
  sh -s -

# 3. 在第二台加入 server cluster
sudo curl -sfL https://get.k3s.io | \
  K3S_TOKEN="<token>" \
  K3S_URL="https://<platform-1>:6443" \
  INSTALL_K3S_EXEC="server --server https://<platform-1>:6443 --node-taint CriticalAddonsOnly=true:NoExecute" \
  sh -s -

# 4. 第三台（如果有）同上
# 5. 验证
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get --raw /api/v1/namespaces/kube-system/endpoints/kube-controller-manager -o yaml
```

⚠️ etcd HA 必须 **奇数** server（1, 3, 5）。2 server 比 1 server 更脆弱——任何一个挂了 etcd 就 lose quorum。

### 5.4 SLB

| 入口 | SLB 监听 | 后端 |
|---|---|---|
| `*.example.com:443` | 443 TCP | 所有 platform 节点 :443 |
| `admin.example.com:443` | 443 TCP | 所有 platform 节点 :443 |
| `auth.example.com:443` | 443 TCP | 所有 platform 节点 :443 |
| API 内部（control-plane） | TCP 8080 + 健康检查 `/healthz` | 所有 platform 节点 :8080 |

DNS 全部指向 SLB 的 VIP。

### 5.5 验证清单

- [ ] 关掉 platform-1 的 docker compose，platform-2 接管所有流量
- [ ] 关掉 platform-1 的 K3s server，集群从 platform-2 继续提供服务
- [ ] 部署一个项目（写 PG / 上 OSS / push 到 ACR / 调度到 worker）能完整跑通
- [ ] 在 platform-2 修改 Settings，platform-1 的 control-plane（重启后）拿到的是新值

## §6 TLS：通配证书 vs 按项目签发

平台支持两种 TLS 模式，**任选一种**（也可以并存：通配管 admin/auth 平台子域、按项目签发管业务 app）。

### 6.1 模式 A：通配证书（DNS-01 / 自带证书）

一张 `*.<base-domain>` 通配证书覆盖所有 app 子域，**适合**：

- 已经有自动续签的通配证书（如 acme.sh + 阿里云 DNS）
- 部署的 app 数量大、Let's Encrypt HTTP-01 限额（50/周/域名）会撞
- 网络环境复杂、:80 不一定公网可达

操作：把 `*.crt` + `*.key` 放到 `/opt/it-iai/tls/`，然后 `sudo /opt/it-iai/deploy/install-tls.sh`。续期换文件后重跑同一个脚本。

### 6.2 模式 B：按项目按需签发（HTTP-01）

cert-manager 安装一次，业务方在 **项目设置 → HTTPS** 自助开启，每个 app 拿到独立证书并自动续期，**适合**：

- 没有 DNS API / 不想接入 DNS provider
- app 数量少（每个域名独立占一个 LE 名额）
- 业务方需要灵活控制要不要 HTTPS

第一次安装：

```bash
sudo ACME_EMAIL=you@example.com /opt/it-iai/deploy/install-cert-manager.sh
```

脚本创建两个 ClusterIssuer：

| 名称 | 用途 | 限额 |
|---|---|---|
| `letsencrypt-prod` | 默认，签真证书 | 50/周/域名 |
| `letsencrypt-staging` | 测试，**不被浏览器信任** | 高 |

控制面默认用 `letsencrypt-prod`。要切到 staging 验证流程，改 `.env`：

```bash
CP_TLS_CLUSTER_ISSUER=letsencrypt-staging
docker compose up -d control-plane
```

### 6.3 单个项目开 HTTPS 的流程

1. 业务方在 Web 进入项目 → **设置 → HTTPS** → 勾选「为本项目启用 HTTPS」→ 保存
2. control-plane 给 Ingress 加上 `cert-manager.io/cluster-issuer` 注解 + `tls:` 段
3. cert-manager 创建 `Certificate` 资源，对每个域名跑 HTTP-01 挑战
4. 约 30 秒后证书写入 `iai-tls-<slug>` Secret，Traefik 自动加载

排查：

```bash
sudo k3s kubectl -n proj-<slug> get certificate
sudo k3s kubectl -n proj-<slug> describe certificate iai-tls-<slug>
sudo k3s kubectl -n cert-manager logs deploy/cert-manager -f
```

### 6.4 HTTP-01 的硬性前置

- `<slug>.<base-domain>` 以及所有自定义域名，都必须解析到平台公网 IP
- :80 **必须**公网可达 —— Let's Encrypt 的验证服务从外网过来，**绕过** VPN、IP 白名单
- 撞限额时换 staging 调试，调通再切回 prod

### 6.5 模式切换

A → B：不用动通配证（仍兜底 TLSStore），跑 `install-cert-manager.sh`，业务方按需开 HTTPS 即可。

B → A：把所有项目设置里的 HTTPS 关掉（control-plane 会移除 `tls:` 段，cert-manager 会回收 Certificate），然后跑 `install-tls.sh` 装通配。

## 故障排查

### 备份失败

- 看 `/var/log/it-iai-backup.log`
- 最常见：磁盘满（先 `df -h` 看 `/var/backups`）
- 第二常见：docker exec 失败（容器 OOM / 重启中）

### 切换到 RDS 之后 control-plane 起不来

```bash
sudo docker compose logs control-plane | tail -50
# 常见：
# - "password authentication failed" → .env 里密码错
# - "no pg_hba.conf entry" → RDS 白名单没加平台节点 IP
# - "SSL required" → 把 ?sslmode=disable 改成 ?sslmode=require
```

### 切换到 OSS 之后 push 卡住

```bash
sudo docker compose logs build-service | tail -50
# 常见：
# - "InvalidAccessKeyId" → key 写错
# - "RequestTimeTooSkewed" → ECS 时间不对，sudo ntpdate ntp.aliyun.com
# - "BucketNotFound" → CP_S3_BUCKET_SOURCE 跟实际 bucket 名不一致
```

### worker 拉不到 ACR 镜像

```bash
# 在 worker 上
sudo k3s crictl pull lb-iai-registry-vpc.cn-hongkong.cr.aliyuncs.com/lb-iai/<image>:<tag>
# 失败的话:
# - registries.yaml 里 endpoint 是否带 https://（ACR 必须 https）
# - VPC 内网 endpoint vs 公网 endpoint 选错
# - K3s 节点是否在同一个 VPC 里
```
