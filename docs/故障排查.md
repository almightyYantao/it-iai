## 二、Deployment 状态机

```
pending      源码 tarball 未上传，等客户端调 /uploaded
  ↓
queued       已上传，等 build-service 拉走
  ↓ build-service.ClaimNextQueued（轮询 2s，FOR UPDATE SKIP LOCKED）
building     正在构建镜像
  ↓
pushing      镜像 push 到 registry，等 reconciler
  ↓ control-plane reconciler（轮询 2s）
deploying    K8s manifests 已 apply，等 pod ready
  ↓
running      上线
```

终态：`running` / `failed` / `superseded`。

**关键：`pending → queued` 必须客户端主动调 `POST /v1/projects/{slug}/deployments/{id}/uploaded`。如果客户端崩了/超时，部署永远停在 pending。**

## 三、按症状速诊

### A. POST /v1/projects/{slug}/deployments → 500

最常见：MinIO 预签名生成失败。
```bash
# 容器内连内部 + 公网 MinIO
docker exec it-iai-control-plane-1 sh -c \
  "wget -qO- --timeout=5 http://minio:9000/minio/health/live -S 2>&1 | head -3; echo ---; \
   wget -qO- --timeout=5 http://47.243.109.253:9000/minio/health/live -S 2>&1 | head -3"
```
- 内部不通 → MinIO 容器挂了，看 `docker logs it-iai-minio-1`
- 公网不通 → NAT hairpin。如果代码没传 region 给 minio-go，`PresignedPutObject` 会调 `GetBucketLocation`，public 客户端连公网 IP 自己回环超时。fix 见 commit `80f91ec`。
- 两边都通 → 看 control-plane 应用日志（除 access log 外的内容），可能是 bucket 不存在 / 凭证错。

### B. Deployment 永远 pending

```bash
# 查记录
docker exec it-iai-postgres-1 psql -U vibedeploy -d vibedeploy \
  -c "SELECT id, status, created_at, queued_at, source_blob_key FROM deployments WHERE id='<uuid>';"
```
- `queued_at IS NULL` → 客户端从未上传源码 / 从未调 /uploaded。让用户重新 `deploy +push`。
- `source_blob_key` 已写但 status 仍是 pending → MinIO 上传失败（presigned URL 没成功 PUT），客户端那边重试。

### C. Deployment 卡在 queued

```bash
docker ps | grep build-service
docker logs it-iai-build-service-1 --tail 100
```
- build-service 没起来 → `docker compose up -d build-service`
- 起着但没拉活 → 看是否 `BS_MAX_CONCURRENT`（默认 2）满了；或 DB 连接池耗尽
- 极少：FOR UPDATE SKIP LOCKED 锁竞争 → 看 `pg_locks`

### D. Deployment 卡在 building

```bash
# build-service 日志（按 deployment id 过滤）
docker logs it-iai-build-service-1 --since 1h 2>&1 | grep <deployment-id>

# 事件流
docker exec it-iai-postgres-1 psql -U vibedeploy -d vibedeploy \
  -c "SELECT ts, source, level, message FROM deployment_events WHERE deployment_id='<uuid>' ORDER BY ts;"
```
通常是用户代码问题（Dockerfile 错、依赖装不上、Buildkit OOM）。

### E. Deployment 卡在 pushing

- registry 连接：`docker exec it-iai-control-plane-1 wget -qO- http://registry:5000/v2/`
- 镜像有没有：`curl http://47.243.109.253:5001/v2/_catalog`

### F. Deployment 卡在 deploying

- pod 状态：`kubectl --kubeconfig /root/.kube/config get pods -A | grep <slug>`
- 看 reconciler 日志（混在 control-plane 日志里）：`docker logs it-iai-control-plane-1 --since 30m | grep -iE "reconcil|<slug>"`

### G. Project URL 502 / 不通

- ingress：`kubectl get ingress -A | grep <slug>`
- 项目状态：`docker exec it-iai-postgres-1 psql -U vibedeploy -d vibedeploy -c "SELECT slug, status FROM projects WHERE slug='<slug>';"`
- pod 还活着吗：`kubectl get pods -n <slug>`

### 4.3 重建并重启服务

```bash
cd /opt/it-iai
git pull --ff-only origin main
docker compose build <svc>
docker compose up -d --no-deps <svc>
```

⚠️ **重启 `control-plane` 后必须连带重启 `web`**：web 容器内 nginx 把 `/v1/*` 反代到 `http://control-plane:8080`，DNS 只在 nginx 启动时解析一次。重建 control-plane 容器后 docker bridge IP 会变（如 172.18.0.7 → 172.18.0.6），nginx 还指着旧 IP，全站 `/v1/*` 返回 502。

正确流程：
```bash
docker compose up -d --no-deps control-plane
docker compose restart web   # 必须！
```

定位线索：浏览器 502，`docker logs it-iai-web-1` 里有 `connect() failed (111: Connection refused) ... upstream: "http://172.18.0.X:8080"`。

## 七、危险操作清单

排查时**默认只读**。下面这些动作之前必须想清楚：

- `docker compose down` — 会拆所有平台容器（包括 postgres，停服全断）
- `docker volume rm it-iai_miniodata` — 删除所有用户源码 + build cache
- `UPDATE deployments SET status=...` — 直接改 DB 可能搞乱状态机
- `kubectl delete namespace <slug>` — 删除用户项目所有资源（pod + svc + ingress + secret）
- 重启 MinIO — 内部 client 缓存的 region/凭证会丢，所有 in-flight presign 失败

凡是改共享状态的操作，先用 `dry-run` / `SELECT` 看好范围再动。
